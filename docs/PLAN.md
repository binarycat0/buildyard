# Buildyard — план и архитектура

Nov 17, 2026 · @binarycat

Личный менеджер сборок Java-проектов: демон + веб-интерфейс. Документ — техзадание для отдельной сессии реализации.

## Как пользоваться этим документом

Это полное техзадание. Новая сессия начинает с фазы 0 и переходит к следующей фазе только после того, как выполнены критерии готовности текущей.

1. Экспортируйте документ в Markdown и положите в новый репозиторий как `docs/PLAN.md`.
2. Откройте новую сессию в этом репозитории и дайте ей стартовый промпт ниже.
3. После каждой фазы сессия коротко отчитывается: что сделано, где решения разошлись с планом. Расхождения вносятся в этот документ.

```text
Прочитай docs/PLAN.md — это техзадание на Buildyard, личный менеджер сборок
Java-проектов (демон + веб-UI). Начни с фазы 0 (спайк). Не начинай фазу N+1,
пока не выполнены критерии готовности фазы N. Решения из раздела
«Ключевые решения» считай принятыми; если хочешь отклониться — сначала спроси.
Тесты на построитель команд и парсеры пиши с первого дня. Отвечай по-русски.
```

## Цель и рамки

Buildyard забирает на себя рутину вокруг Maven в больших мультимодульных проектах, в первую очередь в Dremio. Что он даёт: фоновые сборки, выбор модулей и флагов в UI, сохранённые профили запуска, читаемые логи, историю с таймингами по модулям.

Пользователь один — разработчик на своей машине (macOS или Linux). Демон слушает только localhost.

**Критерий успеха:** типовой цикл «поменял код в двух модулях → пересобрал только нужное без тестов» запускается в 2 клика и не требует помнить флаги.

Не-цели:

- Не CI-сервер: нет агентов, распределённых сборок, пользователей и ролей.
- Не система сборки: Buildyard формирует команду для Maven и наблюдает за ней, сам ничего не компилирует.
- Не IDE: нет редактора, навигации по коду и отладчика.
- Свой кеш сборки не пишем: для этого есть mvnd и maven-build-cache-extension, Buildyard умеет ими пользоваться.

## Ключевые решения

Стек: Go, один бинарник со встроенным UI и SQLite без cgo. Единственная часть на Java — маленькое Maven-расширение для структурированных событий: Maven загружает только Java-классы. Его jar вшивается в бинарник через `go:embed`.

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Язык демона | Go (актуальная стабильная версия) | Один статический бинарник, быстрый старт, мало памяти; горутины удобны для чтения процессов и SSE |
| HTTP | `net/http` со стандартным роутингом по шаблонам (`GET /api/jobs/{id}`); SSE вручную через `http.Flusher` | Без фреймворка: возможностей stdlib хватает |
| Хранилище | SQLite через `modernc.org/sqlite` (чистый Go, без cgo) + `database/sql`; миграции — `pressly/goose` со встроенными SQL-файлами | Кросс-компиляция без C-тулчейна |
| Логи задач | Файлы на диске, в БД только метаданные | Лог Dremio легко набирает десятки МБ |
| Логи демона | `log/slog` в `~/.buildyard/daemon.log` | Stdlib |
| UI | Статические HTML + Alpine.js + ES-модули, вшиты через `go:embed`; JSON API + `EventSource` | Нет node-сборки; тот же API потом использует CLI |
| Чтение pom.xml | `encoding/xml` для `<modules>`, `<profiles>`, `<parent>`, координат | Полная модель Maven не нужна: точную картину даёт расширение |
| События сборки | Своё Maven-расширение на Java (EventSpy), подключается флагом `-Dmaven.ext.class.path`, пишет JSON Lines. Jar вшит в бинарник и распаковывается в `~/.buildyard/ext/` при старте | Точные начало и конец модулей и плагинов без зависимости от формата лога; проект не меняется. Парсинг лога остаётся запасным каналом |
| Исполняемый файл сборки | Автоопределение: mvnd в PATH → `./mvnw` → mvn; можно переопределить для проекта и запуска | mvnd даёт тёплую JVM бесплатно |
| Остановка процессов | `os/exec` + `SysProcAttr{Setpgid: true}`; отмена = SIGTERM (для клиента mvnd — SIGINT) на всю группу, через 10 с SIGKILL | Работает на macOS и Linux, убивает surefire, node и прочие дочерние процессы |
| Команда | Всегда `[]string` argv, без shell | Нет проблем с экранированием и инъекциями |
| CLI и конфиг | Подкоманды на stdlib `flag` (`buildyard serve`, позже `buildyard run`); конфиг `~/.buildyard/config.toml` (`BurntSushi/toml`) | Минимум зависимостей |
| Сборка самого Buildyard | `Makefile`: сначала jar расширения (Maven, `--release 11`), затем `go build`; релизы позже через goreleaser | JDK и Maven на машине и так есть |

## Архитектура

Один процесс-демон на Go стоит между браузером и Maven. Он формирует команду, держит очередь, пишет лог и собирает события из Maven-расширения. Сама сборка остаётся обычным процессом Maven.

_Схема «архитектура Buildyard · демон, 3 сервиса, Maven-адаптер» есть только в исходном документе: https://claude.ai/artifact/RXSQR1bTaMc5MuMefepcdB_

В центре — runner: через него проходит каждый запуск. Анализ проекта только читает файлы и ничего не запускает; исключение — точное обнаружение модулей, которое идёт как обычная задача runner.

Структура репозитория:

```text
buildyard/
  cmd/buildyard/main.go     # serve, open; позже run, install-service
  internal/
    config/                # config.toml, пути ~/.buildyard
    store/                 # SQLite, миграции goose (migrations/*.sql через embed)
    project/               # проекты, профили, shell-команды
    buildtool/             # интерфейс BuildTool, RunSpec, SkipPreset
    buildtool/maven/       # парсер pom, построитель команд, OutputParser
    runner/                # очередь, локи, процессы, логи, события, шина
    scan/                  # сканер пакетов
    changes/               # git diff -> модули
    httpapi/               # маршруты, middleware безопасности, SSE
    ext/                   # jar расширения через go:embed + распаковка
  web/                     # статический UI (Alpine.js) + embed.go
  maven-ext/               # Java: pom.xml + EventSpy
  testdata/                # фикстуры логов и events, sample-maven/
  docs/PLAN.md, docs/SPIKE.md
  Makefile
```

`go:embed` не видит файлы выше каталога пакета. Поэтому `make` сначала собирает `maven-ext/` и копирует jar в `internal/ext/`, и только потом запускает `go build`. Jar лежит в `.gitignore`.

## Модель данных и RunSpec

Всё строится вокруг одного объекта RunSpec — описания запуска. Профиль — это сохранённый RunSpec, задача хранит его снимок на момент запуска. Данные лежат в `~/.buildyard/buildyard.db`, логи — в `~/.buildyard/logs/`, индекс пакетов — в `~/.buildyard/cache/<project>/packages.json`.

```sql
CREATE TABLE project (
  id                INTEGER PRIMARY KEY,
  name              TEXT NOT NULL,
  root_path         TEXT NOT NULL UNIQUE,
  build_tool        TEXT NOT NULL DEFAULT 'maven', -- maven | gradle (позже)
  executable        TEXT,                          -- NULL = авто: mvnd -> ./mvnw -> mvn
  java_home         TEXT,
  env_json          TEXT NOT NULL DEFAULT '{}',
  skip_presets_json TEXT NOT NULL DEFAULT '[]',    -- свои пресеты пропусков
  created_at        TEXT NOT NULL
);

CREATE TABLE module (
  id              INTEGER PRIMARY KEY,
  project_id      INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  group_id        TEXT NOT NULL,
  artifact_id     TEXT NOT NULL,
  rel_path        TEXT NOT NULL,             -- каталог модуля от корня
  packaging       TEXT NOT NULL,
  parent_rel_path TEXT,                      -- для дерева агрегаторов
  profiles_json   TEXT NOT NULL DEFAULT '[]',-- если модуль подключается только профилем
  deps_json       TEXT NOT NULL DEFAULT '[]',-- зависимости внутри реактора
  source          TEXT NOT NULL,             -- static | maven
  discovered_at   TEXT NOT NULL,
  UNIQUE (project_id, group_id, artifact_id)
);

CREATE TABLE run_profile (
  id         INTEGER PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  spec_json  TEXT NOT NULL,                  -- RunSpec
  pinned     INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL,
  UNIQUE (project_id, name)
);

CREATE TABLE job (
  id           INTEGER PRIMARY KEY,
  project_id   INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  profile_id   INTEGER REFERENCES run_profile(id) ON DELETE SET NULL,
  spec_json    TEXT NOT NULL,                -- снимок RunSpec
  argv_json    TEXT NOT NULL,                -- итоговая команда
  status       TEXT NOT NULL,                -- queued|running|succeeded|failed|cancelled|interrupted
  exit_code    INTEGER,
  queued_at    TEXT NOT NULL,
  started_at   TEXT,
  finished_at  TEXT,
  git_head     TEXT,
  log_path     TEXT NOT NULL,
  log_lines    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE job_module (
  job_id      INTEGER NOT NULL REFERENCES job(id) ON DELETE CASCADE,
  module_key  TEXT NOT NULL,                 -- groupId:artifactId
  ord         INTEGER NOT NULL,              -- порядок в реакторе
  status      TEXT NOT NULL,                 -- pending|running|succeeded|failed|skipped
  started_at  TEXT,
  duration_ms INTEGER,
  PRIMARY KEY (job_id, module_key)
);

CREATE TABLE job_problem (
  id         INTEGER PRIMARY KEY,
  job_id     INTEGER NOT NULL REFERENCES job(id) ON DELETE CASCADE,
  module_key TEXT,
  kind       TEXT NOT NULL,                  -- compile_error | test_failure | plugin_error
  file       TEXT,
  line       INTEGER,
  message    TEXT NOT NULL,
  log_line   INTEGER                         -- для перехода к месту в логе
);

CREATE TABLE shell_command (                 -- произвольные команды проекта
  id         INTEGER PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  argv_json  TEXT NOT NULL,
  cwd        TEXT NOT NULL DEFAULT '.',
  UNIQUE (project_id, name)
);
```

Пример RunSpec для Maven:

```json
{
  "kind": "maven",
  "goals": ["install"],
  "modules": {
    "mode": "selected",
    "list": ["com.dremio:dremio-common", "com.dremio:dremio-services-base"],
    "alsoMake": true,
    "alsoMakeDependents": false
  },
  "profiles": [],
  "skips": ["tests", "checkstyle", "javadoc"],
  "properties": {},
  "flags": {
    "offline": true,
    "noSnapshotUpdates": true,
    "threads": "1C",
    "noTransferProgress": true,
    "failMode": "fast"
  },
  "logLevel": "default",
  "executable": null,
  "env": {},
  "extraArgs": []
}
```

`modules.mode` принимает значения `all`, `selected` или `changed`. В режиме `changed` список вычисляется в момент запуска и записывается в снимок задачи. Произвольная команда запускается как `{"kind": "shell", "commandId": 3}` и ссылается на сохранённую `shell_command`. Имена модулей в примере условные.

## BuildTool и Maven-адаптер

Всё, что зависит от системы сборки, сидит за одним интерфейсом. В первой версии реализуется только Maven, но Gradle должен добавляться без правок в runner, API и UI.

```go
type BuildTool interface {
    ID() string                                   // "maven"
    Detect(root string) bool                      // есть pom.xml
    DiscoverStatic(root string) ([]Module, error) // быстро, без запуска сборки
    DiscoverCommand(p Project, profiles []string, out string) []string // argv точного обнаружения
    BuildCommand(p Project, spec RunSpec, eventsFile string) ([]string, error)
    NewOutputParser() OutputParser                // строки лога -> уровень, проблемы, границы модулей
    DefaultSkipPresets() []SkipPreset
}
```

### Обнаружение модулей

1. **Статическое** — по умолчанию и мгновенно. Рекурсивно читаем pom.xml от корня через `encoding/xml`: `<modules>` плюс модули из всех `<profiles>` (с пометкой профиля). groupId наследуется от `<parent>`; `${...}` в координатах подставляем из `<properties>` текущего и родительских pom, что не разрешилось — оставляем как есть.
2. **Точное, через Maven** — по кнопке и при изменении любого pom.xml. Запускаем `validate` с активными профилями, набором пропусков и нашим расширением в режиме `discover`. Расширение на событии SessionStarted пишет реактор: координаты, basedir, packaging, межмодульные зависимости. Если плагины на `validate` окажутся медленными, расширение после записи может прервать сборку; успех тогда определяется по наличию файла (проверить в фазе 0).

### Построение команды

Порядок сборки argv фиксирован, чтобы предпросмотр и тесты были стабильными:

1. Исполняемый файл: `spec.executable` → `project.executable` → автоопределение (mvnd → `./mvnw` → mvn).
2. `-B` всегда: без цветов и интерактива, уровень строки берём из префикса `[INFO]` / `[WARNING]` / `[ERROR]`.
3. Флаги: `-o`, `-nsu`, `-T <n>`, `-ntp`, `-ff` / `-fae`, `-e`.
4. Уровень лога: `quiet` → `-q`, `debug` → `-X`, `default` → ничего.
5. Модули: `-pl :a,:b` плюс `-am` и/или `-amd`; при `mode = all` ничего.
6. Профили: `-P a,!b`.
7. Пропуски из пресетов (таблица ниже) и свойства `-Dkey=value`.
8. Расширение: `-Dmaven.ext.class.path=<jar> -Dbuildyard.events=<файл>`.
9. Цели (`clean install` и т. д.), затем `extraArgs` как есть.

Пресеты пропусков по умолчанию. В настройках проекта их можно редактировать и добавлять свои (например, пропуск сборки UI в Dremio, имя свойства найти в фазе 0):

| Пресет | Аргументы | Замечание |
| --- | --- | --- |
| tests | `-DskipTests` | Тесты компилируются, но не запускаются |
| testCompile | `-Dmaven.test.skip=true` | Ломает модули, зависящие от `test-jar`; в UI предупреждение |
| checkstyle | `-Dcheckstyle.skip` |  |
| spotless | `-Dspotless.check.skip -Dspotless.apply.skip` |  |
| javadoc | `-Dmaven.javadoc.skip` |  |
| sources | `-Dmaven.source.skip` |  |
| enforcer | `-Denforcer.skip` |  |
| license | `-Dlicense.skip -Drat.skip` |  |

### Maven-расширение `buildyard-maven-ext`

- Класс на Java, наследник `AbstractEventSpy`, с аннотациями `@Named @Singleton`. Зависимость `maven-core` 3.9.x в scope `provided`, других зависимостей нет: JSON пишется руками. Компиляция с `--release 11`, чтобы работать с тем JDK, на котором собирается проект.
- Слушает `ExecutionEvent`: SessionStarted, ProjectStarted, ProjectSucceeded, ProjectFailed, ProjectSkipped, MojoStarted, MojoSucceeded, MojoFailed, SessionEnded.
- Пишет JSON Lines в файл из `-Dbuildyard.events`, с flush после каждой строки. Без этого свойства ничего не делает.

```text
{"t":"session","ts":1763400000000,"projects":[{"key":"g:a","dir":"/repo/a","packaging":"jar","deps":["g:b"]}]}
{"t":"project_start","key":"g:a","ts":1763400001000}
{"t":"mojo_start","key":"g:a","mojo":"maven-compiler-plugin:compile","ts":1763400001200}
{"t":"project_end","key":"g:a","status":"succeeded","ms":4210}
{"t":"session_end","ts":1763400090000,"status":"failed"}
```

**Запасной канал.** Если событий нет (расширение не загрузилось), `OutputParser` восстанавливает границы модулей по строкам `Building <name> ... [n/m]` и блоку `Reactor Summary`.

## Исполнение задач

На один проект одновременно выполняется не больше одной задачи, остальные ждут в очереди. Две сборки одного репозитория ломают друг другу `target/`. Глобальный лимит `maxConcurrentJobs` по умолчанию равен 1, потому что все проекты пишут в один `~/.m2`.

Жизненный цикл: `queued → running → succeeded | failed | cancelled`. Если демон упал или был перезапущен, задачи в статусах `queued` и `running` при старте получают `interrupted`. К процессам не переподключаемся, UI предлагает перезапуск.

Запуск задачи:

1. `BuildCommand` строит argv. В `job` записываются argv, снимок RunSpec и `git rev-parse HEAD`.
2. `exec.Cmd`: `Dir` = корень проекта; `Env` = окружение демона + `project.env` + `JAVA_HOME` + `spec.env`; `Stdout` и `Stderr` — один pipe; `SysProcAttr{Setpgid: true}`.
3. Читающая горутина построчно (`bufio.Scanner` с буфером 1 МБ на длинные строки) делает три вещи: дописывает строку в `logs/<job>.log` (номер строки = её порядковый индекс), прогоняет через `OutputParser` и публикует в шину задачи.
4. Вторая горутина читает `events/<job>.jsonl` с хвоста, обновляет `job_module` и публикует события `module`.
5. После `cmd.Wait()` записываются exit code, статус и число строк, задача снимает лок проекта.

Отмена: `syscall.Kill(-pgid, SIGTERM)` на всю группу процессов, через 10 секунд `SIGKILL`. Для mvnd сначала отправляем `SIGINT` клиенту. Сама сборка идёт в долгоживущем демоне mvnd вне нашей группы, так что убивать его нельзя. В фазе 0 нужно проверить, что SIGINT клиенту действительно отменяет сборку.

Шина задачи и SSE:

- У каждой запущенной задачи есть набор подписчиков с буферизованными каналами. Медленный подписчик, чей канал переполнен, отключается; браузер переподключится сам.
- При подключении с `Last-Event-ID: N` сначала отдаются строки из файла начиная с N+1, потом живой поток. Без заголовка — последние 2000 строк, более ранние UI догружает пачками через `GET /log`.
- Для длинных логов держим индекс смещений: байтовая позиция каждой 1000-й строки, чтобы не читать файл с начала.

Очистка: храним последние 200 задач на проект и не больше 2 ГБ логов суммарно. Оба лимита задаются в конфиге.

## Логи и уровни логирования

Maven всегда пишет полный лог в файл, а «уровень» — это в первую очередь фильтр в UI. При падении сборки контекст не теряется. По умолчанию в команду добавляется `-ntp`: он убирает самый объёмный шум — прогресс скачивания.

| Режим `logLevel` | Аргументы | Когда |
| --- | --- | --- |
| default | — | Обычно; фильтр делает UI |
| quiet | `-q` | Лог не нужен совсем; при падении контекста мало |
| debug | `-X` | Диагностика плагинов |
| custom | `-Dorg.slf4j.simpleLogger.log.<logger>=warn` | Точечно приглушить шумный логгер; в фазе 0 проверить, что версия Maven в Dremio это учитывает |

Что делает просмотрщик лога в UI:

- Чипы уровней ERROR / WARN / INFO / DEBUG; уровень строки определяется по префиксу. Строки без префикса (стектрейсы, вывод тестов) наследуют уровень предыдущей.
- Пресет «Только важное» включён по умолчанию: ERROR, WARN, границы модулей, итоги тестов (`Tests run:`), `Reactor Summary`, `BUILD SUCCESS` / `BUILD FAILURE`.
- Заголовки плагинов `--- plugin:goal (id) @ module ---` сворачивают свой вывод в одну строку и раскрываются по клику.
- Поиск, автопрокрутка с переключателем, кнопка «к первой ошибке».
- Панель проблем из `job_problem`. Ошибки компиляции вида `[ERROR] /path/File.java:[12,5] message`, упавшие тесты из блока `Failed tests:` / `Tests in error:`, ошибки плагинов `Failed to execute goal`.
- Пути к файлам кликабельны и открываются в IDE через URL-схему IntelliJ. Какая схема работает на машине, проверить в фазе 7.
- ANSI-последовательности вырезаются на всякий случай, даже с `-B`.

## Сканер пакетов

Сканер строит дерево пакетов из исходников без запуска Maven и показывает его в двух видах: по модулям и общее по всему проекту.

1. Каталоги каждого модуля: `src/main/java`, `src/test/java`, `src/main/kotlin`, `src/test/kotlin`. Сгенерированный код из `target/generated-sources/*` и `target/generated-test-sources/*` помечается как generated и по умолчанию скрыт.
2. В каждом `.java` / `.kt` читаем начало файла до строки `package x.y.z` (регулярное выражение `^\s*package\s+([\w.]+)`, не дальше 64 КБ). Если строки нет, пакет берётся из пути каталога.
3. Обход идёт параллельно: `filepath.WalkDir` и пул воркеров по числу ядер.
4. Дерево — trie по сегментам пакета. Узел хранит полное имя, число классов, модули и вид (main / test / generated). Цепочки с единственным ребёнком схлопываются (`com.dremio.exec` одним узлом), как compact middle packages в IntelliJ.
5. Пакеты, разнесённые по нескольким модулям (split packages), подсвечиваются в общем виде.
6. Кеш в `cache/<project>/packages.json` вместе с mtime файлов. Повторный скан перечитывает только изменившиеся файлы.
7. API отдаёт дерево лениво (дети узла), а не одним гигантским JSON.

Клик по пакету показывает список файлов и кнопку «собрать модули с этим пакетом», которая заполняет выбор модулей в конструкторе запуска. Целевое время для Dremio: полный скан до 10 секунд, повторный до 2 секунд; цифры проверить в фазе 5.

## «Собрать изменённое»

Режим `modules.mode = changed` сопоставляет изменённые файлы с модулями и подставляет их в `-pl`. Для Dremio это, скорее всего, самая полезная функция всего инструмента.

1. Список файлов — объединение:
   - `git diff --name-only <base>...HEAD` — закоммиченное относительно базы;
   - `git diff --name-only` и `git diff --name-only --cached` — незакоммиченное;
   - `git ls-files --others --exclude-standard` — новые файлы.
2. База выбирается в UI из трёх вариантов:
   - **с последнего успешного запуска этого профиля** — по умолчанию; берётся `job.git_head`;
   - от merge-base с upstream-веткой (или `origin/main`);
   - только незакоммиченное.
3. Файл принадлежит модулю с самым длинным совпадающим префиксом `rel_path`. Файлы вне модулей игнорируются, кроме корневого `pom.xml` и `.mvn/*`: их изменение превращается в «собрать всё» с предупреждением.
4. Изменённый `pom.xml` модуля включает сам модуль и даёт подсказку включить `-amd`.
5. Перед запуском UI показывает полученный список модулей и позволяет его поправить.

Переключатели `-am` и `-amd` остаются за пользователем. Без `-am` сборка рассчитывает, что зависимости уже лежат в `~/.m2` после предыдущего `install`. `-amd` нужен, чтобы прогнать тесты зависимых модулей.

## HTTP API и события

Весь функционал доступен через JSON API под `/api`. Этим же API пользуются UI и будущий CLI. Ошибки возвращаются как `{"error": "<code>", "message": "..."}` с соответствующим HTTP-кодом.

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/projects` | Список проектов с последней задачей |
| POST | `/api/projects` | Добавить `{name, rootPath}`: определить систему сборки, статическое обнаружение модулей |
| GET / PATCH / DELETE | `/api/projects/{id}` | Проект и его настройки |
| GET | `/api/projects/{id}/modules` | Дерево модулей |
| POST | `/api/projects/{id}/modules/refresh?mode=static\|maven` | Пересканировать модули |
| GET | `/api/projects/{id}/packages?node=&module=` | Дети узла дерева пакетов |
| POST | `/api/projects/{id}/packages/rescan` | Пересканировать пакеты |
| GET | `/api/projects/{id}/changes?base=` | Изменённые файлы и модули |
| GET / POST | `/api/projects/{id}/profiles` | Профили запуска проекта |
| PUT / DELETE | `/api/profiles/{id}` | Изменить или удалить профиль |
| GET / POST | `/api/projects/{id}/commands` | Произвольные команды проекта |
| POST | `/api/projects/{id}/preview` | RunSpec → `{argv, display}` без запуска |
| POST | `/api/projects/{id}/jobs` | Запустить: `{spec}` или `{profileId}` |
| GET | `/api/jobs?projectId=&status=&limit=` | История задач |
| GET | `/api/jobs/{id}` | Задача, её модули и проблемы |
| POST | `/api/jobs/{id}/cancel` | Отменить |
| POST | `/api/jobs/{id}/rerun` | Перезапустить с тем же снимком RunSpec |
| GET | `/api/jobs/{id}/log?from=&limit=&levels=` | Строки лога пачкой |
| GET | `/api/jobs/{id}/stream` | SSE: лог, модули, статус |
| GET | `/api/events` | SSE: статусы всех задач для глобальной строки задач |
| GET | `/api/health` | Версия и состояние демона |

События в `/api/jobs/{id}/stream` (`event:` → `data:`):

- `log` — `{n, text, level}`; `id:` события равен номеру строки `n`, это даёт догрузку через `Last-Event-ID`;
- `module` — `{key, ord, total, status, ms}`;
- `problem` — `{kind, module, file, line, message, logLine}`;
- `status` — `{status, exitCode}`, последнее событие, после него сервер закрывает поток.

Каждые 15 секунд сервер шлёт комментарий `: ping`, чтобы соединение не закрывалось по таймауту.

## UI: экраны

UI состоит из четырёх экранов и строки задач вверху, которая видна везде. Главный экран — конструктор запуска: до нажатия Run видна точная итоговая команда.

- **Строка задач** — запущенные и ожидающие задачи с прогрессом n/m. Клик ведёт на экран задачи. Данные идут из `/api/events`.
- **Проекты** — карточки: имя, путь, статус и длительность последней задачи, закреплённые профили кнопками. Кнопка «Добавить проект»: поле пути, проверка, что там есть pom.xml.
- **Проект** — вкладки:
  - *Запуск.* Слева дерево модулей с чекбоксами, поиском и кнопкой «выбрать изменённые». Справа цели (чипы clean / compile / install / verify / test и свои), чекбоксы пресетов пропусков, флаги, профили `-P`, таблица свойств `-D`, уровень лога, исполняемый файл. Внизу предпросмотр команды с кнопкой копирования и кнопки Run и «Сохранить как профиль».
  - *Профили.* Список с кнопками Run / Edit / Clone / Pin.
  - *История.* Таблица задач: статус, профиль, модули, длительность, коммит, время. Выбрав две задачи, можно сравнить тайминги по модулям.
  - *Пакеты.* Дерево с переключателем «по модулям / общее», поиском и переключателем generated.
  - *Настройки.* Исполняемый файл, `JAVA_HOME`, окружение, редактор пресетов пропусков, произвольные команды.
- **Задача** — шапка (статус, команда, время, Cancel / Rerun), полоса прогресса n/m, горизонтальные полоски времени по модулям (текущий модуль подсвечен), просмотрщик лога и панель проблем.

Лог рендерится виртуальным списком: в DOM только видимые строки, иначе браузер задохнётся на логе Dremio. Горячие клавиши: `r` — перезапустить текущую задачу, `/` — поиск в логе, `e` — к следующей ошибке.

## Демон, конфигурация, безопасность

Демон запускает произвольные команды, поэтому даже на localhost его API закрыт токеном и защищён от запросов из чужих вкладок браузера. Иначе любой сайт может дёрнуть `127.0.0.1:7777`.

**Запуск.** `buildyard serve` слушает `127.0.0.1:7777` (порт задаётся в конфиге). Второй экземпляр не стартует: `~/.buildyard/daemon.lock` с PID через `flock`. При старте демон распаковывает вшитый jar расширения в `~/.buildyard/ext/buildyard-maven-ext-<version>.jar`, если его там нет.

Каталог данных:

```text
~/.buildyard/
  config.toml
  token              # chmod 600
  daemon.lock
  daemon.log
  buildyard.db
  ext/buildyard-maven-ext-<version>.jar
  logs/<job>.log
  events/<job>.jsonl
  cache/<project>/packages.json
```

```toml
port = 7777
maxConcurrentJobs = 1

[retention]
jobsPerProject = 200
maxLogBytes = "2GB"

[defaults]
executable = "auto"   # auto | mvn | mvnd | mvnw
flags = ["-ntp"]
```

**Безопасность:**

- Bind только на `127.0.0.1`, слушать `0.0.0.0` нельзя даже через конфиг.
- Токен генерируется при первом запуске (32 байта из `crypto/rand`). `buildyard serve` и `buildyard open` печатают ссылку `http://127.0.0.1:7777/?token=...`. Первый заход ставит cookie `HttpOnly; SameSite=Strict` и делает редирект без токена в URL. API принимает cookie или заголовок `X-Buildyard-Token`.
- Заголовок `Host` должен быть `127.0.0.1:<port>` или `localhost:<port>` (защита от DNS rebinding). На изменяющих запросах `Origin` должен совпадать с самим демоном (CSRF). CORS не включаем.
- Произвольные команды запускаются только по id сохранённой `shell_command`, а не сырым текстом в запросе на запуск. `extraArgs` в RunSpec передаются Maven как аргументы, без shell.

**Автозапуск (фаза 7).** `buildyard install-service` пишет launchd-plist в `~/Library/LaunchAgents/` на macOS или user-юнит systemd в `~/.config/systemd/user/` на Linux. Демон наследует окружение сервиса, а не шелла. Поэтому `PATH` и `JAVA_HOME` надо явно задавать в конфиге или в настройках проекта.

## Тестирование, риски, открытые вопросы

Надёжность инструмента держится на трёх чистых функциях: построителе команд, парсере вывода и сопоставлении файлов с модулями. Они покрываются табличными тестами с первого дня.

**Тесты:**

- Unit (табличные тесты Go): `BuildCommand` (RunSpec → argv), `OutputParser` на фикстурах из `testdata/`, сопоставление файлов с модулями, разбор pom.xml, сканер пакетов на мини-дереве.
- Интеграционные (билд-тег `integration`): маленький Maven-проект из трёх модулей в `testdata/sample-maven/` (один модуль падает на компиляции по свойству) с реальным запуском mvn и расширения.
- HTTP: `httptest` на маршруты, авторизацию, проверки Host / Origin, SSE с `Last-Event-ID`.
- Ручной чеклист на Dremio в конце каждой фазы — её критерий готовности.

| Риск | Чем опасен | Что делаем |
| --- | --- | --- |
| mvnd не подхватывает `-Dmaven.ext.class.path` или кеширует расширение между сборками | Нет событий и таймингов с mvnd | Проверить в фазе 0; запасной парсер лога; версия в имени jar |
| Maven-обнаружение модулей медленное из-за плагинов на `validate` | Дерево модулей грузится долго | По умолчанию статический режим и кеш; Maven-режим по кнопке и при изменении pom; прерывание сборки из расширения |
| Формат вывода меняется между Maven 3.9 и Maven 4 | Запасной парсер ломается | Основной канал — события расширения; фикстуры на обе версии |
| Параллельные сборки разных проектов пишут в общий `~/.m2` | Случайные падения | `maxConcurrentJobs = 1` по умолчанию |
| Демон исполняет команды по HTTP | Запуск кода с чужой веб-страницы | Только localhost, токен, проверки Host / Origin, только сохранённые shell-команды |
| Демон как сервис не видит `PATH` и `JAVA_HOME` из шелла | mvn / java не находятся | Явные пути в конфиге; в `/api/health` показать, что нашлось |
| Проект разрастается до «ещё одного CI» | Ничего не доделано | Фазы с критериями; всё вне таблицы требований — в `docs/IDEAS.md` |
